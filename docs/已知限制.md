# 已知限制與後續建議

## 網頁版本身的限制

| 項目 | 限制 | 影響 | 因應方式 |
|------|------|------|----------|
| 背景定位 | 手機關閉螢幕或切換到其他 App 時，網頁無法繼續記錄軌跡 | 巡邏軌跡會有中斷 | 巡邏中自動保持螢幕常亮；據點掃描當下一定記錄位置，防代巡判定不受影響 |
| NFC 標籤 | iPhone 瀏覽器不支援讀取 NFC | 室內高風險點無法改用 NFC | 目前以 QR＋位置＋照片驗證；若需 NFC，第二階段改做原生 App |
| 假定位偵測 | 網頁無法偵測手機是否安裝假 GPS 軟體 | 有心人可偽造位置 | 照片浮水印、自拍確認、時間間隔判定作為補強；主管覆核 |
| 臉部辨識 | 已改為伺服器驗證（正式模式）；示範模式仍只在手機端確認 | iPhone 的 Face ID 失敗時可改輸入手機密碼通過，知道手機密碼的人仍可冒用 | 搭配巡邏中隨機自拍；請巡邏員勿將手機密碼告知他人 |
| 自拍比對 | 由主管以人工比對，尚無自動人臉辨識 | 需要主管投入時間 | 每場只要求 1 次；若需自動比對，需另評估人臉辨識服務與個資影響 |
| 推播通知 | 主管需開著後台才會看到 SOS 警示 | 主管離開電腦時可能漏看 | 第二階段串接 LINE 通知或 Email |

## 示範模式的限制

1. 資料只存在單一瀏覽器，換電腦或清除瀏覽資料就會消失。
2. 預設啟用「模擬定位」，讓不在校園也能測試；正式模式一律使用真實 GPS。
3. 據點座標是元智大學附近的示意位置，不是實際據點位置。

## 已測試項目

1. 資料庫規則：以 PostgreSQL 16 實際執行，測試 QR 金鑰錯誤、超出範圍、重複掃描、冒用他人照片路徑、未填異常說明、未填漏巡原因、巡邏員無法讀取金鑰、無法修改紀錄、無法查看他人資料、一人一機切換。全部通過。
2. 操作流程：以瀏覽器自動化測試巡邏員端與管理後台，共 38 個步驟，包含模擬相機拍照、SOS 長按、換機核准、新增據點與人員。全部通過，無程式錯誤。
3. QR 標籤：列印標籤經掃描解碼後內容一致。

## 尚未測試，需於試行時確認

1. 實際 iPhone、Android 手機的相機、定位與生物辨識。
2. 校園各據點的 GPS 誤差，用來調整範圍半徑。
3. 地下室、機房等無訊號處的離線暫存與補傳。
4. Supabase 正式環境：上述資料庫規則是在本機以模擬環境測試，部署後需再做一次完整流程。

## 日報表自動寄送

1. 已測試：Excel 產生（瀏覽器與伺服器兩端）、勤務日時間計算（夜班跨日歸入前一日）、權限（巡邏員看不到設定、只有管理者可修改）。
2. 尚未測試：實際寄信。需要學校提供寄件網域並設定 Resend 後，才能做完整測試。
3. 示範模式只能下載 Excel，不會寄信。
4. 23:59 寄出當天報表時，跨過午夜的夜班巡邏會分在兩天的報表：每筆定點紀錄只計入發生當天，未巡據點計入巡邏結束當天。23:59 當下仍在進行的巡邏會標示「進行中」。
5. 若 23:59 寄送失敗（例如寄信服務暫時異常），系統不會在隔天補寄，需由班長在後台選擇日期後按「立即寄送」。

## 自行註冊與臉部辨識登入

1. 已測試：申請、班長核准與退回、一次掃臉報到並開始巡邏、重新開啟需再掃臉、臉部辨識失敗無法進入、其他手機無法沿用他人臉部登入、伺服器驗證簽章與防重送。
2. 伺服器端判定「已通過臉部辨識」：手機自行回報的結果一律不採信，以伺服器 15 分鐘內的驗證紀錄為準。
3. 尚未測試：實機 iPhone Face ID 與 Android 指紋（以瀏覽器模擬驗證器測試）；正式 Supabase 環境的完整流程。
4. 申請註冊不需登入，任何人都能送出申請；因需班長核准才會生效，風險可控。若出現大量垃圾申請，可再加上邀請碼。

## 第二階段建議功能

1. 漏巡提醒：依班表時段，超過時間未開始巡邏即通知主管。
2. LINE 推播：SOS、緊急異常即時通知（Email 日報表已完成）。
3. ~~生物辨識伺服器端驗證~~（已完成）。
4. 異常事件自動轉總務報修系統。
5. 月報表 PDF 自動產生，供保全契約驗收使用。
6. 據點確認方式選項（2026-10 討論，暫維持 QR Code）：
   - 戶外點改「GPS 定位打卡＋照片」，免貼 QR，網頁版即可做，約半天。
   - 有門禁讀卡機的點，改用門禁刷卡紀錄，需門禁廠商提供資料。
   - 改原生 App 後可用 NFC 標籤或藍牙信標自動感應。
